# Phase 2C handoff: Windows XP x64 OpenGL on GA104

Updated November 16, 2026.

### Source trace after `.231`: confirmed boot instance corruption

- Confirmed overlapping GPU writes: `nvx_gsp.c:NvxGspCreateGraphicsProbe`
  assigns the boot GR instance/RAMFC to scratch `+0xa000` (line 1556).
  Later `nvx_disp_rpc.c:NvxGspInitDisplayChannels` reads 16 pages of cleared
  display instance memory into exactly scratch `+0xa000..+0xafff` (lines
  174-176). This overwrites the live GR instance with zeroes. In `.231`, the
  boot GR triangle passes at log line 478, display instance initialization
  completes at 651, and a subsequent boot submission times out and receives
  ChID 2 RC 31. This is a concrete allocation-lifetime bug and a strong causal
  explanation for the later boot failure; correction still needs hardware
  validation. Upstream `kchannelAllocMem_GM107` owns a separate instance
  allocation and RAMFC subdescriptor; display readback cannot reuse that live
  allocation. Use dedicated, lock-protected readback backing for display.
- `nvx_ce.c:NvxGspVerifyGrBacking` also uses `+0xa000`, but its call precedes
  `NvxGspCreateGraphicsProbe` in `NvxGspCreateObjects`. That use is not the
  same post-allocation overwrite. Account for call order when auditing aliases.
- The private client recreation failure is independently established:
  `.231` frees ChID 10, recreates it successfully at the RPC level, then fails
  `NvxGrVerifyClientQueue` before its seven-dword SET_OBJECT/semaphore probe
  completes. `NvxWinsysOpenNouveauChannel` consequently fails and xf86drm
  reports `channel_result=2`; Mesa screen creation fails before application
  shaders/draws. The private instance has different backing from boot scratch,
  so the display overwrite does not by itself prove the cause of this stall.
- Correct the earlier interpretation of `.230`: the paired FIFO-data EHeap
  only changes CPU bookkeeping; its association is not consumed by hardware
  setup or the kick. Its presence did not establish a channel-recreation fix.
  Upstream also supports normal ChID reuse; merely recycling ID 10 is not a bug.
- Concrete submission difference: upstream `channelFillGpFifo` in
  `gpu/mem_mgr/channel_utils.c` writes GPFIFO, flushes CPU WC stores, writes
  USERD PUT, flushes again, and calls `kbusFlushPcieForBar0Doorbell_HAL` before
  ringing. XP uses CPU barriers and `nvx_openrm_kick`, which additionally
  writes `runlistBase+0x90` and has no equivalent explicit PCIe flush in that
  path. Applicability of the flush depends on mapping/cache attributes; this
  remains a hypothesis, not a proven cause.
- Upstream `kchannelDestruct_IMPL` sends channel FREE, detaches GR mappings,
  releases HAL resources/group membership, then releases ChID. XP performs
  STOP/EVICT/FREE and releases its backing but does not implement the full
  host mapping graph. Audit this together with fresh/reused instance contents
  and PTE visibility. `RAMFC_CHID=0` is an XP diagnostic at a hardcoded offset,
  not sufficient proof that RM failed to assign the requested hardware ID.
- This was source/log analysis only; no driver changes or new hardware run.

### `.228` channel-recreation fix and hardware result

## 1. Latest Run & Artifacts
### Upstream comparison after `.228`

- Highest-priority custom boundary: `nvx_gr_clients.c:NvxGspOpenClientChannel` builds physical context initialization and VA-only PROMOTE requests itself. Upstream `kernel_graphics_context.c` tracks mappings/refcounts with VA_LIST and detaches/unmaps through `shrkgrctxDetach_IMPL` (around 3530), subject to `kgrctxShouldCleanup`. XP has no equivalent host mapping ownership graph. Shared global backing plus private context backing needs explicit ownership accounting; a generic EVICT is not equivalent to all host destructor work. This is a confirmed architectural difference, not a proven explanation of the stalled queue.
- `nvx_openrm_shim.c:nvx_openrm_channel_memory` hardcodes descriptor sizes, offsets and cache attributes. Upstream `_kchannelSendChannelAllocRpc` (kernel_channel.c around 2421) obtains these from real FIFO instance/USERD/TSG memory descriptors. The physical-descriptor RPC itself is upstream behavior for GSP clients; supplying descriptors is not inherently a divergence. Reuse allocator/HAL sizing and descriptor construction where feasible, with XP supplying the actual coherent allocations.
- `nvx_openrm_policy.c:nvx_openrm_kick` calls the imported TU102 doorbell implementation, then adds a custom MMIO write to runlistBase+0x90. That extra write is not part of the compared upstream helper. A previous doorbell-only candidate failed boot, so removing it blindly is not a validated fix; audit the physical BAR0 versus upstream virtual-register mapping contract first.
- `nvx_openrm_containers.c` now mirrors the ChID and FIFO-data heaps, but is not the complete CHID_MGR. Upstream also clears FIFO data, drops isolation IDs and supports retained ID references. The paired heaps did not stop the `.231` ChID 10 recreation stall; refcount/retainer and full channel teardown behavior remain open comparisons.
- Native clear now requires its own ready client channel, and its test explicitly opens the owner channel. The legacy `NvxGspSubmitUserOperation` path still targets boot GR and is associated with the later ChID 2 FIFO MMU fault; changing native-clear ownership does not eliminate all boot submissions. Route diagnostics through an owned client lease and keep one submission implementation.
- Practical reuse: continue importing self-contained OpenRM policy/HAL functions and containers with real XP OS adapters. Full `kchannelConstruct`/destruct, GR mapping and memory ownership routines require the connected NVOC/resource-server/memdesc/VASpace objects; the current small policy views cannot safely stand in for that object graph. Do not claim that a wrapper around existing custom code ports those subsystems.

## 3. Previously Identified Issues (Prior to v3.0.0.227)
1. **FIFO MMU Fault / Unbound Instance Block on Native Clear**:
   - Observed in `.220` through `.226`: In `test_gpu_accel`, ad-hoc tokens without leased channels triggered `NvxGspSubmitNvc0NativeClear()` falling back to boot ChID 2. Because client ChID 10 was promoted via `GPU_PROMOTE_CTX`, submitting to ChID 2 triggered an MMU fault on GPFIFO (`0x10009000`, type 4 `FAULT_UNBOUND_INST_BLOCK`, RC 31), causing subsequent channel quarantine.
2. **`wglgears` Selecting GDI Generic**:
   - Observed in `.225` and `.226`: `glxgears_main.cpp` started searching at format 37. When Windows XP GDI returned format 3 (`PFD_GENERIC_FORMAT`), the format scan completely skipped hardware Mesa formats 1..36, falling back to GDI Generic software emulation.
3. **32-bit WOW64 Context Creation Failure (Error 126)**:
   - Observed when running 32-bit OpenGL applications: `Wow6432Node` pointed to 64-bit `nvxogl64.dll`, causing PE architecture mismatch on `LoadLibrary`.
4. **Context Recreation Stalls & Error 183**:
   - Observed when reopening WGL contexts or creating subsequent client channels after teardown without complete backing resource reclamation.
5. **Scratch Page Aliasing**:
   - Identified in `.224` / `.225`: Runtime CE push slots at `scratch+0xd000` overlapped the boot GR channel's RM method buffer (`scratch+0xc000..0xdfff`), and upload diagnostic readbacks used `scratch+0xa000` (GR RAMIN). Fixed by relocating CE completion fences to `+0x3400` and diagnostic readbacks to `+0xe000`.

## 4. Design Architecture

The NVX driver stack enables hardware-accelerated 2D and 3D graphics on Windows XP Professional x64 Edition running on modern Ampere (GA104) hardware. The stack consists of a dual-head XDDM display driver, an NT 5.2 miniport driver hosting an OpenRM GSP client, and a customized Mesa Gallium user-mode driver stack.

### Key Architectural Layers

1. **User-Mode OpenGL ICD (`nvxogl64.dll`)**:
   - Built from Mesa 27.0.0-devel using MinGW-w64 targeting NT 5.2.
   - Includes Mesa's native Gallium WGL frontend and `nvc0` driver.
   - Emulates the Linux DRM/KMS Nouveau interface in user mode using `nvx_xf86drm.c`, `nvx_winsys.c`, and `nvx_nouveau_*.c`.
   - Converts Gallium pipe operations into user buffer leases and NVC0 pushbuffer command packets forwarded directly to the miniport driver via `IOCTL_NVX_3D_SUBMIT_BATCH`.

2. **Kernel Miniport Driver (`nvxmp.sys`)**:
   - Implements standard Windows XP Video Port (XDDM) interfaces.
   - Manages an internal GSP firmware runtime derived from open-gpu-kernel-modules, executing RISC-V GSP firmware (`gsp_ga104.bin`).
   - Implements GPU virtual address space (GART and VRAM) management, channel leasing, and fence tracking.
   - Validates NVC0 pushbuffers in kernel mode prior to writing to the GSP ring buffer, preventing GPU faults and illegal subchannel assignments.

3. **Display Subsystem (`nvxdisp.dll` & `nvx_disp_rpc.c`)**:
   - Provides 2D acceleration (solid fills, screen-to-screen copies via 2D and Copy Engines).
   - Manages dual-head display hardware (Head 0 and Head 1) using GSP display RPC commands (`NvxNativeSetSecondaryScanout`).
   - Bridges fallback VBE INT10 mode tables with full DMT mode tables up to 2560x1440 and 4K.

## 5. Relevant Files & Code Locations

### 1. Kernel-Mode Miniport Driver (`src_driver/`)
- **`src_driver/nvxmp.c`**: Core driver entry, XDDM callbacks (`HwVidInitialize`, `HwVidStartIO`), 3D IOCTL dispatchers, buffer lifecycle management (`Nvx3dAllocBuffer`, `Nvx3dFreeBuffer`), client session open/close, GART page reclamation, and batch submission.
- **`src_driver/nvx_gsp.c`**: Host-GSP communication, command message queue (MSGQ), channel allocation, pushbuffer kick-off (`NvxGspSubmitNvc0Batch`), native clear execution (`NvxGspSubmitNvc0NativeClear`), and release fence tracking.
- **`src_driver/nvx_gr_clients.c`**: Graphics client channel allocation, initialization, promotion (`GPU_PROMOTE_CTX`), teardown, and channel lookup (`NvxGspFindAnyReadyClientChannel`).
- **`src_driver/nvx_ce.c`**: Copy Engine routines, runtime uploads/downloads, staging synchronization, and completion fences.
- **`src_driver/nvx_disp_rpc.c`**: Dual-head display RPC controls, scanout configuration, EDID parsing, and secondary head management (`NvxNativeSetSecondaryScanout`).
- **`src_driver/nvx_gr_context.c` / `nvx_gr_context.h`**: GART heap management (`NvxGartReserve`, `NvxGartRelease`) and GPU 3D graphics context structures.
- **`src_driver/nvx_3d_abi.h`**: Public user/kernel interface definition: IOCTL codes (`IOCTL_NVX_3D_*`), buffer structures, batch headers, and kernel pushbuffer validator logic (`Nvx3dValidateNvc0ObjectBindingsEx`).
- **`src_driver/nvx_mmu.c`**: Page directory and page table structure management for Ampere MMU.

### 2. User-Mode Display Driver (`src_disp/`)
- **`src_disp/nvxdisp.c`**: XDDM display driver entry points (`DrvEnableDriver`, `DrvEnablePDEV`, `DrvCompletePDEV`).
- **`src_disp/opengl.c`**: Driver escape handling (`DrvEscape`) for OpenGL DDI discovery and ICD binding.
- **`src_disp/screen.c`**: Mode enumeration, desktop surface allocation, and dual-monitor coordination.
- **`src_disp/blt.c`**: Accelerated 2D blits, color fills, and copy-engine offload.

### 3. User-Mode Mesa Gallium & DRM Compatibility (`mesa_patches/`)
- **`mesa_patches/nvx_xf86drm.c`**: Emulated `libdrm` interface for Windows XP x64, translating DRM GEM allocations and pushbuffer flushes to Windows IOCTLs.
- **`mesa_patches/nvx_winsys.c`**: Nouveau winsys implementation connecting the Gallium `pipe_screen` to the emulated DRM device.
- **`mesa_patches/0031-nouveau-xp-use-m2mf-linear-copy.patch`**: Diverts `copy_data` to `nvc0_m2mf_copy_linear` (Subchannel 2) to eliminate CE/P2MF hazards on XP.
- **`mesa_patches/0030-nouveau-xp-direct-linear-transfer-map.patch`**: Permits direct linear transfer maps for staging resources.
- **`mesa_patches/0001-xp-win32-shims.patch`**: Core NT 5.2 / Win32 portability shims and compatibility overrides across Mesa.
- **`mesa_patches/0002-nvx-gallium-bridge.patch`**: WGL ICD bridge export (`DrvCopyContext`, `DrvCreateContext`, `DrvSetContext`, etc.).

### 4. Build, Packaging, and Test Harness (`test/` & `dist_full/`)
- **`test/3d_tests/glxgears_main.cpp`**: 64-bit and 32-bit standalone WGL gears test utility.
- **`test/test_full_driver.sh`**: Compiles driver components, verifies import tables, updates the guest disk image, and launches the QEMU/KVM VFIO guest.
- **`test/update_disk_driver_user.sh`**: Mounts guest disk image via guestmount and updates system binaries and registry keys.
- **`dist_full/nvx.inf`**: Windows XP setup information file registering driver services, display resolution defaults, and 64-bit OpenGL ICD registry entries.
- **`dist_full/install.bat`**: Deployment batch script for installing driver and configuring registry inside the VM.
