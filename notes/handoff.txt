## Design Architecture

The NVX driver stack enables hardware-accelerated 2D and 3D graphics on Windows XP Professional x64 Edition running on modern Ampere (GA104) hardware. The stack consists of a dual-head XDDM display driver, an NT 5.2 miniport driver hosting an OpenRM GSP client, and a customized Mesa Gallium user-mode driver stack.

### Key Architectural Layers

1. **User-Mode OpenGL ICD (`nvxogl64.dll`)**:
   - Built from Mesa 27.0.0-devel using MinGW-w64 targeting NT 5.2.
   - Includes Mesa's native Gallium WGL frontend and `nvc0` driver.
   - Emulates the Linux DRM/KMS Nouveau interface in user mode using `nvx_xf86drm.c`, `nvx_winsys.c`, and `nvx_nouveau_*.c`.
   - Converts Gallium pipe operations into user buffer leases and NVC0 pushbuffer command packets forwarded directly to the miniport driver via `IOCTL_NVX_3D_SUBMIT_BATCH`.

2. **Kernel Miniport Driver (`nvxmp.sys`)**:
   - Implements standard Windows XP Video Port (XDDM) interfaces.
   - Manages an internal GSP firmware runtime derived from open-gpu-kernel-modules, executing RISC-V GSP firmware (`gsp_ga104.bin`).
   - Implements GPU virtual address space (GART and VRAM) management, channel leasing, and fence tracking.
   - Validates NVC0 pushbuffers in kernel mode prior to writing to the GSP ring buffer, preventing GPU faults and illegal subchannel assignments.

3. **Display Subsystem (`nvxdisp.dll` & `nvx_disp_rpc.c`)**:
   - Provides 2D acceleration (solid fills, screen-to-screen copies via 2D and Copy Engines).
   - Manages dual-head display hardware (Head 0 and Head 1) using GSP display RPC commands (`NvxNativeSetSecondaryScanout`).
   - Bridges fallback VBE INT10 mode tables with full DMT mode tables up to 2560x1440 and 4K.

## Relevant Files & Code Locations

### 1. Kernel-Mode Miniport Driver (`src_driver/`)
- **`src_driver/nvxmp.c`**: Core driver entry, XDDM callbacks (`HwVidInitialize`, `HwVidStartIO`), 3D IOCTL dispatchers, buffer lifecycle management (`Nvx3dAllocBuffer`, `Nvx3dFreeBuffer`), GART page reclamation, and batch submission.
- **`src_driver/nvx_gsp.c`**: Host-GSP communication, command message queue (MSGQ), channel allocation, pushbuffer kick-off (`NvxGspSubmitNvc0Batch`), and release fence tracking.
- **`src_driver/nvx_disp_rpc.c`**: Dual-head display RPC controls, scanout configuration, EDID parsing, and secondary head management (`NvxNativeSetSecondaryScanout`).
- **`src_driver/nvx_gr_context.c` / `nvx_gr_context.h`**: GART heap management (`NvxGartReserve`, `NvxGartRelease`) and GPU 3D graphics context structures.
- **`src_driver/nvx_3d_abi.h`**: Public user/kernel interface definition: IOCTL codes (`IOCTL_NVX_3D_*`), buffer structures, batch headers, and kernel pushbuffer validator logic (`Nvx3dValidateNvc0ObjectBindingsEx`).
- **`src_driver/nvx_mmu.c`**: Page directory and page table structure management for Ampere MMU.

### 2. User-Mode Display Driver (`src_disp/`)
- **`src_disp/nvxdisp.c`**: XDDM display driver entry points (`DrvEnableDriver`, `DrvEnablePDEV`, `DrvCompletePDEV`).
- **`src_disp/opengl.c`**: Driver escape handling (`DrvEscape`) for OpenGL DDI discovery and ICD binding.
- **`src_disp/screen.c`**: Mode enumeration, desktop surface allocation, and dual-monitor coordination.
- **`src_disp/blt.c`**: Accelerated 2D blits, color fills, and copy-engine offload.

### 3. User-Mode Mesa Gallium & DRM Compatibility (`mesa_patches/`)
- **`mesa_patches/nvx_xf86drm.c`**: Emulated `libdrm` interface for Windows XP x64, translating DRM GEM allocations and pushbuffer flushes to Windows IOCTLs.
- **`mesa_patches/nvx_winsys.c`**: Nouveau winsys implementation connecting the Gallium `pipe_screen` to the emulated DRM device.
- **`mesa_patches/0031-nouveau-xp-use-m2mf-linear-copy.patch`**: Diverts `copy_data` to `nvc0_m2mf_copy_linear` (Subchannel 2) to eliminate CE/P2MF hazards on XP.
- **`mesa_patches/0030-nouveau-xp-direct-linear-transfer-map.patch`**: Permits direct linear transfer maps for staging resources.
- **`mesa_patches/0001-xp-win32-shims.patch`**: Core NT 5.2 / Win32 portability shims and compatibility overrides across Mesa.
- **`mesa_patches/0002-nvx-gallium-bridge.patch`**: WGL ICD bridge export (`DrvCopyContext`, `DrvCreateContext`, `DrvSetContext`, etc.).

### 4. Build, Packaging, and Test Harness (`test/` & `dist_full/`)
- **`test/build_mesa_xp64.sh`**: Cross-compiles Mesa using MinGW-w64 and Meson into `nvxogl64.dll`.
- **`test/apply_mesa_xp_patches.sh`**: Validates `mesa/` submodule commit and cleanly applies patches `0001` through `0031`.
- **`test/test_full_driver.sh`**: Compiles driver components, verifies import tables, updates the guest disk image, and launches the QEMU/KVM VFIO guest.
- **`test/update_disk_driver_user.sh`**: Mounts guest disk image via guestmount and updates system binaries and registry keys.
- **`dist_full/nvx.inf`**: Windows XP setup information file registering driver services, display resolution defaults, and 32/64-bit OpenGL ICD registry entries.

## What Has Been Implemented & What Was Tried

### 1. Engine Hazard & Pushbuffer Linear Transfers (v3.0.0.194)
- **Implemented**: Created `mesa_patches/0031-nouveau-xp-use-m2mf-linear-copy.patch` and integrated it into `test/apply_mesa_xp_patches.sh` and `test/build_mesa_xp64.sh`.
- **Change**: In `mesa/src/gallium/drivers/nouveau/nvc0/nvc0_transfer.c:nvc0_init_transfer_functions`, configured `nvc0->base.copy_data = nvc0_m2mf_copy_linear` for XP / Windows builds instead of `nve4_m2mf_copy_linear`.
- **Rationale**: Routes linear staging copies through the M2MF/P2MF subchannel (subchannel 2) rather than the asynchronous Copy Engine (subchannel 4), ensuring sequential execution on the same engine and avoiding cross-engine hazards with P2MF uploads.

### 2. GART Heap Recycling & Page Management (v3.0.0.194)
- **Implemented**: Restored `NvxGartRelease(&engine->GspGartHeap, saved.GartFirstPage, saved.GartPageCount)` in `src_driver/nvxmp.c:Nvx3dFreeBuffer` across both pending and immediate unmap branches once GSP unmap and TLB invalidation confirm.
- **Implemented**: In `src_driver/nvxmp.c:IOCTL_NVX_3D_CLIENT_CLOSE`, added automated cleanup iterating over active buffers belonging to the terminating client session and freeing them to ensure no GART pages remain quarantined or leaked across process restarts.

### 3. Channel Object Binding Validation (v3.0.0.194)
- **Implemented**: In `src_driver/nvxmp.c:IOCTL_NVX_3D_SUBMIT_BATCH`, updated the `requireGraphicsBinding` condition passed to `Nvx3dValidateNvc0ObjectBindingsEx`:
  ```c
  (engine->Nvx3dChannelBoundToken != header.ClientToken) && (engine->GspGraphicsObjectClassEngineId == 0)
  ```
  This prevents the kernel validator from rejecting batches from subsequent client tokens when the hardware channel already has the 3D graphics class (`0xC797`) bound.

### 4. Dual Monitor & 1440p Resolution Support (v3.0.0.193)
- **Implemented**: In `src_driver/nvxmp.c:HwVidInitialize`, upgraded fallback/degraded VBE INT10 mode lists to authentic GA104 DMT modes up to 2560x1440 and 4K so the primary display is not capped at 1080p.
- **Implemented**: In `src_driver/nvx_disp_rpc.c:NvxNativeSetSecondaryScanout`, updated Head 0 default target resolution to 2560x1440 when EDID timing is not preset.

### 5. Registry & WOW64 Integration (v3.0.0.193 - v3.0.0.194)
- **Implemented**: Registered OpenGL ICD entries under both `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\OpenGLDrivers\nvxdisp` and `HKLM\SOFTWARE\Wow6432Node\Microsoft\Windows NT\CurrentVersion\OpenGLDrivers\nvxdisp` across `dist_full/nvx.inf`, `dist_full/install.bat`, and `test/update_disk_driver_user.sh` (including explicit parent key hierarchy creation in hive imports).

### 6. Pushbuffer Ring Architecture & Hardware Synchronization (v3.0.0.192)
- **Implemented**: A 4-slot ring buffer for command batch submission in `src_driver/nvxmp.c` and `src_driver/nvx_gsp.c`, allowing queued pushbuffers to cycle with release fences instead of reallocating single slots.
- **Implemented**: Removed invalid direct PBDMA MMIO writes from guest miniport, delegating work submission and GP_PUT advances cleanly to GSP-managed channels.

## Current Issues and Candidate Fix (v3.0.0.195)

1. **GPU submissions stall before their release fence completes (confirmed in `.194`)**:
   - First logged failure is fence `0x3`, push buffer VA `0x15F90000`; later fences time out too. USERD GET remains at `4` while PUT advances, with no PGRAPH trap reported. `wglgears` eventually reports only one frame in 483 seconds.
   - **Candidate fix**: `mesa_patches/nvx_winsys.c` now refuses to recycle one of its four staging pushbuffer BOs if that slot's previous fence does not complete within five seconds. Previously the wait result was ignored, so the CPU could overwrite pushbuffer memory that the GPU might still be reading. This should prevent queue corruption after a stall; it is not yet proven to fix the initial GPU stall.
   - **Next diagnostic**: Use the `.195` run to correlate the exact miniport IOCTL status with the existing PBDMA, USERD, and failed-stream dump. Do not increase the submission timeout as a substitute for fixing the queue.

2. **Mesa reports `kernel rejected pushbuf: Operation not permitted` (confirmed in `.194`)**:
   - The ICD and Nouveau screen initialize and renderer reports `NV170`; the pushbuf path reaches miniport submission, but Mesa's error text alone does not identify which validation or submission boundary returned failure.
   - **Candidate diagnostics**: `src_driver/nvxmp.c` now logs rejection status and batch size/counts for validation and submit IOCTL failures, including explicit ownership and packet/address rejection messages. The existing `Nouveau pushbuf item kind=6` trace indicates whether object translation failed, submit failed, or succeeded. The `.195` trace should distinguish a malformed/rejected batch from a GPU timeout returned as a submission failure.

3. **Firmware assertion count increases during 3D startup (confirmed in `.194`)**:
   - Counter rises from 1 during startup to 3 as graphics work begins. No accompanying PGRAPH trap was captured, so the cause is not established. Compare `.195` assertion/RC-fault messages with the first failing batch before changing channel setup.

4. **VRAM allocation pressure (observed in `.194`, causality unknown)**:
   - Two 64 MiB VRAM allocations fail while GART allocations continue. Track against the first submission timeout, but current evidence does not show this caused it.
