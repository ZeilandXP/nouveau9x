# Windows XP x64 OpenGL handoff

Updated November 16, 2026. Latest test build: **3.0.0.236**.

### v3.0.0.236 shadow coherency fix (hardware test in progress)

- Replaced access-flag-gated whole-BO shadow uploads with changed-dword
  publication for every mapped BO referenced by a submission. This covers
  upstream access=0/cached-map CPU writes and preserves unchanged GPU words.
- Each mapped shadow tracks a baseline. The first publication initializes
  previously undefined backing to match the shadow (including zero stores).
  GPU read refresh merges unpublished CPU words instead of discarding them.
  Partial uploads keep the shadow's read-freshness fence unchanged, so a later
  CPU read still refreshes untouched words changed by the GPU.
  Changed uploads wait for the previous BO fence; failed final unmaps retain
  the shadow for retry rather than dropping unpublished data.
- The first 48 changed ranges per process log pushbuf item kind=19:
  a=BufferId, b=offset, c=uploaded bytes, d=map access, e=GPU readback success,
  f=sample matches CPU. Up to 64 bytes are independently read back per range;
  a mismatch fails publication. Samples do not validate complete geometry.
- Host checks passed before the final new-allocation zero regression was
  added; the full runner repeats all checks. Added regression coverage for
  writes via READ-labelled maps, preserving GPU changes elsewhere in a BO,
  unchanged repeat flushes, merge on refresh, and initial backing contents.
- Hardware outcome pending. Two build attempts were stopped before deployment
  to cover initial-zero and partial-upload freshness edge cases. No guest boot
  occurred in those attempts; the final build repeats all host checks.

## Current status

The XP x64 miniport and Mesa Nouveau WGL ICD run on a passthrough RTX 3070. The
bounded NVC0 test submits hardware draws, verifies green pixels by readback,
and completes its semaphore. Standalone WGL gears has reached the `NV170`
renderer on real hardware, but image correctness, repeat context creation,
and the complete application path remain unresolved.

### Latest allocation experiment: v3.0.0.235

The prior XP patches `0023` and `0024` forced WGL resources toward shared/linear
GART storage and forced depth memory kind to zero. Those patches are no longer
applied by the XP Mesa build scripts. Nouveau GEM requests now carry tile mode
and `tile_flags[15:8]` memory kind across the XP DRM shim and the fixed-size
miniport ABI. The miniport installs the requested kind in the VRAM leaf PTEs,
invalidates the VA space once per range, and restores kind zero before freeing.
Kinded allocations are rounded to the 64 KiB PTE granularity. GART allocations
remain linear and reject kind/tile requests rather than silently misreporting
placement. ABI version is now 22.

Host checks passed: `make -C src_driver check`, including the new ABI and GEM
shim cases for kind preservation, invalid kinds, and honoring alignment. The
Mesa submodule is clean after the build scripts restored their temporary XP
patches. The XP import/subsystem audit passed for all packaged binaries.

VFIO log: `test_logs/v3.0.0.235-20261116-174247.log` (`vm_serial.log` points to
the latest run). Hardware evidence:

- The first 64-bit gears run selected a non-generic format, reported
  `GL_RENDERER = NV170`, and completed 106 frames in 6 seconds (17.667 FPS).
- The miniport logged normal Nouveau PTE-kind installation for VRAM allocations
  (kinds 6 and 3) and reset those ranges on free. No image capture was made, so
  this does not prove the gears are drawn correctly. The user reports that the
  gears looked the same after this allocation change; the missing/red gear
  geometry is still present. Treat this experiment as an allocation-path
  validation, not a visual correctness fix.
- `[NVX_3D_RESULT] PASS` and `GR RESULT: hardware triangle draw, green pixel
  readback, and semaphore completed successfully!`.
- The normal framebuffer heap could not fit Nouveau's 0x04080000-byte TLS BO;
  it fell back to GART, with placement reported as GART.
- The full runner exited with the hardware-OpenGL gate failing. Antigravity's
  separate audit reports `[OPENGL_RESULT] SOFTWARE` in one launch and fails to
  create the ICD context (`error=126`) in another. A later gears launch does
  reach `NV170`, but a subsequent context attempt fails with error 183. The
  64-bit test process exits with `0xC0000005`; D3D9 reports no HAL / returns
  unavailable. These are separate failures from the successful first gears
  render and bounded NVC0 test.
- The log reports one firmware assertion. Display verification shows both
  heads active. The full suite is **not passing**.

## Issues to resolve

1. **Visual correctness of gears:** the normal-allocation experiment did not
   change the user's visual result. Capture the actual window or GPU readback
   while gears runs and compare red/green/blue gear coverage. The prior user
   image showed most of the red gear missing. Renderer string and frame count
   alone do not prove correct geometry/depth/presentation. Next trace vertex,
   index, depth, and color-target state/submission through the draw and swap;
   do not continue treating allocation kind as the leading explanation without
   evidence from a captured target.
2. **32-bit ICD missing:** the error-183 gears launch is the 32-bit executable,
   not proof that a second 64-bit context cannot be created. Only PE32+ x64
   `nvxogl64.dll` and `nvxmesa.dll` are built/deployed. `install.bat` explicitly
   deletes the Wow6432Node ICD registration. The x86 gears loader tries these
   x64 DLL names and has no packaged x86 ICD. Display-driver pixel formats can
   still report PFD_GENERIC_FORMAT=NO without a usable x86 ICD. Build/deploy an
   XP-compatible x86 Mesa ICD and register it in the 32-bit registry view.
   Error 183 is not sufficient to diagnose a channel collision: the test does
   not clear last error before context creation or report each DLL load error.
3. **Antigravity OpenGL audit:** its launch can use software rendering or fail
   with error 126 before creating a context. Determine why its selected pixel
   format / ICD load differs from the standalone gears path, then ensure the
   test reports the renderer for the same successful context.
4. **D3D9:** current package reports no Direct3D HAL and the 64-bit test later
   crashes. This is not covered by the OpenGL allocation change.
5. **VRAM capacity:** the 128 MiB VRAM aperture does not fit the 64.5 MiB TLS
   allocation after current reservations, so the shim retries it in GART.
   Keep that fallback truthful and validate other tiled or kinded large BOs
   cannot accidentally fall back to incompatible GART storage.
6. **Normal allocation validation:** kinds 3 and 6 match this upstream Mesa's
   TU102+ storage selection (S8Z24 and generic color respectively). The earlier
   expectation of color kind 0xfe was incorrect for Ampere. Still validate
   resource addresses, tile mode, and transferred pixels against the actual BOs.

### Code comparison: remaining drawing corruption

Analysis only; no code change or new hardware run in this revision.

- Strongest concrete semantic mismatch is CPU mapping/coherency. Upstream
  `nouveau.c:nouveau_bo_map` always uses PROT_READ|PROT_WRITE and MAP_SHARED;
  its `access` argument controls synchronization, not mapping permissions.
  Upstream `nouveau_buffer.c` legitimately maps with access=0 then writes:
  migration at lines 822-825, user upload at 892-895, scratch runout at 988.
  XP patches 0012/0028 instead turn access=0 into MAP_READ. The submission
  loop (`nvx_xf86drm.c:942`) skips shadows without WRITE, and
  `NvxNouveauBoFlush` also returns success without uploading them. This can
  submit stale/zero vertex or other buffer data despite a completed fence.
  Existing vertex-address range uploads and the immediate-triangle special
  case cover selected packet shapes; they do not establish general equivalence
  to upstream shared mappings. This is a confirmed contract mismatch, but its
  responsibility for the observed gears image still needs a targeted check.
- The shadow design also uploads entire WRITE-mapped BOs before GPU reads.
  Upstream maps the same backing directly; it does not overwrite an entire BO
  from a separate CPU snapshot on submission. Mixed CPU/GPU-written or
  suballocated BOs need dirty-range/ownership handling to avoid overwriting
  valid GPU results. Simply marking every shadow writable is insufficient.
- Target selection itself looks consistent: upstream
  `nvc0_miptree.c:tu102_choose_tiled_storage_type` selects color kind 6 and
  S8Z24 kind 3, and upstream `nvc0_state_validate.c` emits RT/ZETA addresses,
  dimensions, format, and tile mode. Current logs show color kind 6.
  OpenRM/UVM's Turing PTE builder confirms kind and physical-address fields,
  but OpenRM does not generate Nouveau's OpenGL framebuffer/draw state.
- XP patch 0020 bypasses upstream WGL end-of-frame waiting for Nouveau, even
  though the WGL presenter now reads pixels on the CPU. Presentation still
  calls the upstream texture transfer path, which synchronizes its readback;
  therefore the bypass is an audit target, not proof of a race. Check the
  staging copy fence and CPU shadow refresh before attributing missing parts
  to presentation. The native color target has not been captured yet.
- Next discrimination: compare CPU and GPU bytes for each actual gears
  vertex/index/constant range immediately before consumption, including
  access=0 and cached mappings. Then capture the rendered target through
  Nouveau's tiled-to-linear transfer before StretchDIBits, and compare with
  the displayed image. This distinguishes input corruption from depth/render
  state and presentation without guessing from frame completion.
