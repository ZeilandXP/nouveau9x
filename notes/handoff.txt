# Windows XP x64 OpenGL handoff

Updated November 16, 2026. Latest package: **3.0.0.235**.

## Current status

The XP x64 miniport and Mesa Nouveau WGL ICD run on a passthrough RTX 3070. The
bounded NVC0 test submits hardware draws, verifies green pixels by readback,
and completes its semaphore. Standalone WGL gears has reached the `NV170`
renderer on real hardware, but image correctness, repeat context creation,
and the complete application path remain unresolved.

### Latest allocation experiment: v3.0.0.235

The prior XP patches `0023` and `0024` forced WGL resources toward shared/linear
GART storage and forced depth memory kind to zero. Those patches are no longer
applied by the XP Mesa build scripts. Nouveau GEM requests now carry tile mode
and `tile_flags[15:8]` memory kind across the XP DRM shim and the fixed-size
miniport ABI. The miniport installs the requested kind in the VRAM leaf PTEs,
invalidates the VA space once per range, and restores kind zero before freeing.
Kinded allocations are rounded to the 64 KiB PTE granularity. GART allocations
remain linear and reject kind/tile requests rather than silently misreporting
placement. ABI version is now 22.

Host checks passed: `make -C src_driver check`, including the new ABI and GEM
shim cases for kind preservation, invalid kinds, and honoring alignment. The
Mesa submodule is clean after the build scripts restored their temporary XP
patches. The XP import/subsystem audit passed for all packaged binaries.

VFIO log: `test_logs/v3.0.0.235-20261116-174247.log` (`vm_serial.log` points to
the latest run). Hardware evidence:

- The first 64-bit gears run selected a non-generic format, reported
  `GL_RENDERER = NV170`, and completed 106 frames in 6 seconds (17.667 FPS).
- The miniport logged normal Nouveau PTE-kind installation for VRAM allocations
  (kinds 6 and 3) and reset those ranges on free. No image capture was made, so
  this does not prove the gears are drawn correctly. The user reports that the
  gears looked the same after this allocation change; the missing/red gear
  geometry is still present. Treat this experiment as an allocation-path
  validation, not a visual correctness fix.
- `[NVX_3D_RESULT] PASS` and `GR RESULT: hardware triangle draw, green pixel
  readback, and semaphore completed successfully!`.
- The normal framebuffer heap could not fit Nouveau's 0x04080000-byte TLS BO;
  it fell back to GART, with placement reported as GART.
- The full runner exited with the hardware-OpenGL gate failing. Antigravity's
  separate audit reports `[OPENGL_RESULT] SOFTWARE` in one launch and fails to
  create the ICD context (`error=126`) in another. A later gears launch does
  reach `NV170`, but a subsequent context attempt fails with error 183. The
  64-bit test process exits with `0xC0000005`; D3D9 reports no HAL / returns
  unavailable. These are separate failures from the successful first gears
  render and bounded NVC0 test.
- The log reports one firmware assertion. Display verification shows both
  heads active. The full suite is **not passing**.

## Issues to resolve

1. **Visual correctness of gears:** the normal-allocation experiment did not
   change the user's visual result. Capture the actual window or GPU readback
   while gears runs and compare red/green/blue gear coverage. The prior user
   image showed most of the red gear missing. Renderer string and frame count
   alone do not prove correct geometry/depth/presentation. Next trace vertex,
   index, depth, and color-target state/submission through the draw and swap;
   do not continue treating allocation kind as the leading explanation without
   evidence from a captured target.
2. **Context recreation:** later WGL context/channel creation still fails with
   error 183. Trace WGL ICD context allocation/deletion, channel lease close,
   and resource cleanup across sequential applications; do not attribute this
   to the initial successful gears session.
3. **Antigravity OpenGL audit:** its launch can use software rendering or fail
   with error 126 before creating a context. Determine why its selected pixel
   format / ICD load differs from the standalone gears path, then ensure the
   test reports the renderer for the same successful context.
4. **D3D9:** current package reports no Direct3D HAL and the 64-bit test later
   crashes. This is not covered by the OpenGL allocation change.
5. **VRAM capacity:** the 128 MiB VRAM aperture does not fit the 4 MiB TLS
   allocation after current reservations, so the shim retries it in GART.
   Keep that fallback truthful and validate other tiled or kinded large BOs
   cannot accidentally fall back to incompatible GART storage.
6. **Normal allocation validation:** the host GEM test proves ABI propagation,
   but the VFIO run's observed kinds are 3 and 6. Confirm color resources with
   kind 0xfe are requested, mapped, used by rendering, and read back correctly.

## Next steps

1. Add focused logging of each GEM_NEW request/result (domain, size, alignment,
   tile mode, kind) and correlate allocation IDs with the WGL target/depth
   resources. Do not log every small GART allocation in the serial stream.
2. Capture an image or readback from the first successful `NV170` gears run;
   compare target and depth surfaces before/after draw and swap.
3. Trace the second context's error 183 against `DrvCreateContext`/`DrvDeleteContext`,
   channel open/close tokens, and resource ownership.
4. Fix the Antigravity ICD load/context path and keep the strict hardware gate
   enabled for the next hardware run.
5. Address D3D9 separately after the OpenGL context and image path are stable.

  truthful placement response.
